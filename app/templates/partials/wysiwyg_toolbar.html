{# The rich-text toolbar, written once. It was defined in public/page.html and reimplemented, smaller, for the blog editor -- two toolbars for one job, which is the drift this project keeps warning about. One macro now, included by both, so a button added here appears in both places. `include_image` / `include_icon` are the only difference between the callers: the live page can upload an image into the words and insert an icon from its own grid; an admin form has no upload target and carries its own icon control. Everything else is identical, deliberately. The behaviour lives in static/js/wysiwyg-commands.js, shared the same way -- see that file for why a command needs a caller to say what to do afterwards. `include_layout` is a third: alignment, a font and a colour are things an EMAIL cannot honour -- every client that strips a stylesheet also ignores most of them, and the newsletter's serialiser has no way to write them down. A control that is thrown away on save is a control that lies, so the newsletter turns that group off and keeps exactly the seven the vocabulary supports. #} {% macro wysiwyg_toolbar(include_image=true, include_icon=true, include_layout=true) %}
